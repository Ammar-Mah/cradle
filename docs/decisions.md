# Framework decisions

Durable decisions only. Newest last.

| Date | Decision | Reason | Alternatives that mattered | Packages |
| --- | --- | --- | --- | --- |
| 2026-09-24 | Local repository layout overrides northstar §4.1 where they differ: source in this folder, a disposable sandbox WordPress in `wp/`, representative site in `sites/sandbox/`, mirrored by `scripts/sync.php` (also run automatically by a Claude Code PostToolUse hook). | The operator requires development in this folder with every change moved into `wp/` for testing, and a sandbox that behaves like a real install. | Symlinks (rejected: Windows developers must not need symlinks, §5.5); editing inside wp/ (rejected: sandbox is disposable). | all |
| 2026-09-24 | Target WordPress 7.1.2 (current on 2026-09-24 per api.wordpress.org), PHP floor 8.3, MySQL 8.4 sandbox. Multisite refused at activation. | §2.2 compatibility policy. | — | all |
| 2026-09-24 | Every package header uses `Update URI: false`; slugs `cradle*` were free on wordpress.org on 2026-09-24 but this prevents a future directory plugin with the same slug from being offered as an "update". | Prevents update hijacking by slug collision. | Private update server (not built; §22.1 forbids fabricating endpoints). | all |
| 2026-09-24 | Core boots the registry on `plugins_loaded` priority 5 but calls module `boot` callbacks on `init` priority 0. | WordPress 6.7+ reports translation calls before `init`; modules register translated UI, post types and blocks inside boot. | Booting modules on plugins_loaded (produced `_load_textdomain_just_in_time` notices). | core, add-ons |
| 2026-09-24 | Each settings section is one registered option with a declared field schema plus reserved `_revision`/`_schema` keys; unknown keys are dropped. | Settings API compliance, stale-edit detection, field-level validation, no catch-all blob (§6.1). | One option per field (no atomic revision check). | core |
| 2026-09-24 | Capabilities are granted once per capability to declared roles and the grant is remembered. | Respects later administrator removals; avoids re-granting on every request. | Grant on every activation (overrides admin choices). | core |
| 2026-09-24 | Jobs/locks use dedicated tables with atomic UPDATE claims and fencing counters. | §15.4 requires atomic claims and expired-worker protection; options/transients cannot provide it. | Transients (read-then-write race). | core, migration, dummy-content |
| 2026-09-24 | Private files: `CRADLE_PRIVATE_DIR` outside the web root when defined; otherwise a random uploads subfolder with deny rules that counts as protected only after a live HTTP probe proves denial. | §15.5 / §20.4; an Apache rule does not protect Nginx. | Always uploads (unsafe on Nginx). | core, migration, translations |
| 2026-09-24 | The Gutenberg adapter lives in `cradle-blocks`; feature plugins with blocks declare the module dependency `blocks`. Components ship `component.json` + render callable + `blockDir`. | §3.1 assigns the adapter to cradle-blocks; one registration path for all component blocks. | Each plugin registering blocks itself (duplicated mapping logic). | blocks, hero, social, site |
| 2026-09-24 | `cradle/feature-card` stores attributes in the block comment and semantic fallback markup via `save()`; the PHP render service is authoritative while active. Plain-text props are entity-decoded by core and `save()` decodes entities. | Saved fallback (§7.5) plus stability when kses encodes attributes for users without `unfiltered_html` (found in editor testing). | Fully dynamic block (no fallback); sourced attributes (not available to PHP render). | core, blocks |
| 2026-09-24 | Theme and core plugin share the `cradle` text domain as mandated by §4.2; add-ons use `cradle-<feature>`. | Spec requirement. Cradle Translations catalogs group by domain, so overrides cover both. | — | theme, core |
| 2026-09-24 | Cradle Login serves the unmodified `wp-login.php` at `home_url('/<slug>/')` without rewrite rules; recovery via `CRADLE_DISABLE_CUSTOM_LOGIN`, the `cradle_login_disable_routing` filter, or deactivating/renaming the add-on. No bypass query string. | No rewrite flushes; route cannot be stranded by stale rules; §10.3 recovery without DB edits. | Rewrite-rule route (needs flushes, can go stale). | login |
| 2026-09-24 | Provisioned records carry protected meta `_cradle_source_key`; the site registry option `cradle_site_provisioning` stores ID + content hash; edited records are reported as conflicts, never overwritten without `--replace`. | §8.7 idempotent provisioning that preserves administrator edits. | Matching by title/slug (fragile, overwrites edits). | site plugin, duplicate |
| 2026-09-24 | Sandbox `wp-config.php` sets `WP_DEVELOPMENT_MODE=theme`; deployments bump theme `Version` when templates/patterns/theme.json change. | WordPress caches theme pattern lists by version; new patterns were invisible in development. | Clearing caches manually. | themes |
| 2026-09-24 | Add-on activation may call `Capabilities::grant( $cap, $roles, $owner )`, which now records the grant like core's one-time policy. | Login add-on had to duplicate bookkeeping. | — | core, add-ons |
| 2026-09-24 | Admin simplified after review: no core settings page (activity retention is fixed at 90 days / 5000 rows, developer filters only), no "Components & cleanup" page and no "Block conversion" page. The per-module data policy on deletion is a "When deleted" column on Cradle → Modules (`delete_plugins`); stale component overrides are listed on Cradle → Developer; usage scan and static export stay as APIs. Core schema 3 revokes `cradle_manage_components`; blocks schema 2 revokes `cradle_convert_components`. | The owner found these screens unused or confusing; the capabilities they protected are kept out of every role. | Keep the screens behind a developer flag (more surface, same confusion). | core, cradle-blocks, cradle-admin |
| 2026-09-24 | **Superseded the same day (see below).** Hero content is a custom post type `cradle_hero_item`: one post per slide ("Slider 1", "Slider 2", …), visibility = post status, order = `menu_order`, content = one validated meta object. The Hero slider block is the builder component: all published items in their Order (with a maximum) or chosen items in a chosen order; a block that chose items never falls back to all items. Replaces the 0.1 slide-group model (several slides in one post), without migration because 0.1 was never released. | Owner request: hero items are content items editors manage like posts, and the slider is placed where needed rather than being a fixed part of the theme. | Keep slide groups (one post holding a list); a generic post with a "hero" type (would mix hero slides into the blog). | cradle-hero, sites/sandbox |
| 2026-09-24 | Settings sections accept `menu_parent` (default `cradle`), so a module can list its settings page in its own menu (for example under a post type menu; the retired hero plugin was the first user). | Keeps a feature's screens together. | Always under Cradle. | core, cradle-hero |
| 2026-09-24 | The hero slider is a normal Gutenberg component in `cradle-blocks` (`cradle/hero-slider`), not a plugin: its slides are published entries of any viewable post type (latest with count/order/term, or chosen and ordered in the block) showing featured image, title, excerpt and link; every style and behavior option is a block attribute set by the page editor. The Cradle Hero plugin, its `cradle_hero_item` post type, slider-defaults settings and capability were retired; this overrides northstar §17's separate hero plugin. | Owner decision: sliders are page-building components with posts as content, not a feature plugin or theme part. | Keep a hero post type (extra content model to maintain); global defaults page (settings outside the editor). | cradle-blocks, sites/sandbox |
| 2026-09-24 | The Cradle admin shell is Overview (theme check, modules with state/activation/"When deleted", status report) and Activity. The separate Modules page and the Developer page were removed; developer facts (storage protection, component override problems) go to the status report and Site Health. | Owner found Overview and Modules duplicated and the Developer page unnecessary. | Keep a developer page behind `manage_options`. | core |
| 2026-09-24 | Cradle Fonts retired: custom fonts are managed with the WordPress Font Library. | Owner: the core Font Library already uploads, installs and activates fonts; the plugin's extras (licence notes, format allow-list, preloading) did not justify a plugin. Overrides northstar §18. | Keep as an optional add-on. | cradle-fonts (removed) |
| 2026-09-24 | **Superseded the same day (see below).** Site content types are Cradle Content definitions by default; a site plugin is optional and only for custom code (and then declares types through `cradle_content/code_definitions`). The sandbox has no site plugin. The Content types screen also lists types registered by other code, read-only. Trade-off: while Cradle core/Content is missing, their types are paused (data kept) instead of staying online. | Owner: fewer plugins and every content type visible under Content types; site code cannot go into core (shared by all sites, replaced on update). | Keep code-registered types in a site plugin. | cradle-content, sites/sandbox, skills |
| 2026-09-24 | The Cradle admin shell is Overview only (plus add-on pages) in the fixed order Overview, Branding & admin, Content types, Migration, Translations, Dummy content, Social, Duplicate, Login (`Admin::MENU_ORDER`). Activity is kept as a service without a page. | Owner request. | Keep the Activity page. | core |
| 2026-09-24 | Cradle Translations ships built-in German and Arabic example languages (`examples/*.json`) covering every framework string; they are always present and fill only entries without a translation or draft. Test suites use other locales (de_CH, fr_FR, ar_EG). | Owner: examples that are always there, with proper translations. | Ship .po/.mo files per package (not editable in the Translations screen). | cradle-translations, tests |
| 2026-09-24 | A Cradle website has **no site plugin at all**. Everything site-specific lives in the child theme: brief (`northstar.md`), state (`docs/`), design, site components (`components/<slug>/` + `blocks/<slug>/`, registered by the child's `functions.php` on `cradle/booted`; core accepts descriptors inside the active theme), small site code (`inc/`) and the content-model baseline (`content/content-types.json`). Site content types are Cradle Content definitions; while Cradle Content is inactive their URLs 404 (content kept) — accepted by the owner. | Owner: one fewer package per site; the child theme is the website. | Optional site plugin for custom code (kept a second place for site code); code-registered types in the child theme (invisible under Content types, lost on theme switch). | theme, core, cradle-content, sites/sandbox, skills |
| 2026-09-24 | The parent theme creates and maintains website child themes: it ships the starter (`starter/child-theme/`, PHP files as `.tpl` so they never run inside the parent) and the CLI generator `bin/child-theme.php` (`new`; `check --add-missing` after parent updates; never overwrites; reserved framework slugs refused; exits without output over the web). `templates/` and `scripts/new-site.php` were removed; `scripts/build.php` builds the blank starter ZIP with the same generator. | Owner: LLM-driven site generation must work from any Cradle install, not only from the framework repository. | Keep the starters and generator in the repository only (unavailable on real sites); a WordPress admin screen that writes theme files (web-writable code). | theme, scripts, skills |
| 2026-09-25 | Website child themes are **thin**: site data only (brief, records, `theme.json`, necessary template/part/pattern overrides, `assets/`, `components/`), no framework code. The parent's `inc/child-theme.php` loads `assets/css/design.css`, `assets/css/site.css`, `assets/js/site.js` and `components/<slug>/` (+ `blocks/<slug>/`) by convention; website rules live in the parent's `docs/child-themes.md` and each child's `AGENTS.md` only points there. These conventions are a contract: renaming or removing one needs an upgrade note and keeps the old path working for a release. | Owner: the parent and plugins are still being developed; updating them must not break a website's work. Code or rules copied into each child go stale and diverge. | Starter with enqueue/registration code in `functions.php` (copied per site, never updated); site PHP in `inc/`. | theme, sites/sandbox, skills |
| 2026-09-25 | Builds include a copy-in kit `cradle-kit-<date>.zip` (`wp-content/themes/{cradle,cradle-child}` + every Cradle plugin), a blank child `cradle-child` ("Cradle Child", `siteId` `set-on-first-use`; the agent names it on first use) and an update bundle `cradle-update-<date>.zip` (parent + plugins, no child). | Owner: start and update a website by copying files, without running commands. A kit re-extracted for an update would replace a child still named `cradle-child`, so updates use a bundle that cannot contain a child. | Only per-package ZIPs plus the generator; one kit for both (overwrites the site's child). | scripts, theme |
| 2026-09-25 | A child theme's `northstar.md` starts empty and is the owner's document (any structure); the brief outline lives in the parent as `docs/website-brief.md`, used by agents as a checklist to ask about gaps. Agents never rewrite the owner's brief unless asked. | Owner: they arrive with their own northstar file; a pre-filled template in the child was confusing and would have to be merged or overwritten. | Keep the outline in the child's `northstar.md`; put it in the child's `AGENTS.md` (copied per site, goes stale). | theme, skills |
| 2026-09-25 | The repository is versioned with git and hosted as a private GitHub repository. `.gitignore` excludes `wp/`, `wp-target/` and `dist/` (the same paths `scripts/build.php` leaves out of the source bundle); release ZIPs are attached to GitHub Releases. `.gitattributes` stores text with LF endings. `README.md` explains the concept, installation and the LLM website workflow, and how to recreate the sandbox after cloning. | Owner: push the project to GitHub. The sandboxes hold `wp-config.php` credentials/salts and generated uploads; `dist/` is reproducible build output. | Committing `dist/` (binary churn in history); committing the sandboxes (secrets, ~330 MB of WordPress core). | all |
